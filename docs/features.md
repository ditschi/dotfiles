# Features

Notes on individual features. The full list with defaults is the feature table [`ansible/group_vars/all/features.yml`](../ansible/group_vars/all/features.yml); see [host-config.md](host-config.md) for how features are selected.

Private hosts get `monitoring` (Telegraf) by default, installed from the InfluxData apt source. Config names are resolved **only** in `tasks/resolve_monitoring.yml` from the hardware and the device (not in the CLI). The inputs are the local files under `ansible/roles/monitoring/files/`; with `INFLUX_TELEGRAF_CONFIG_BASE` set, the remote Influx configs replace them. The output comes from the Bitwarden item `influxdb-telegraf-write` (see [Secrets / Bitwarden](secrets.md)). Telegraf runs only with an output; otherwise it stays stopped and `machine attention` says why. See [ansible/roles/monitoring/README.md](../ansible/roles/monitoring/README.md).

Feature `gnome`: besides the apt packages (Flameshot, extension manager), `machine` installs and enables GNOME Shell extensions without root (Ddterm, gTile, Clipboard Indicator, Quick Settings Audio Panel, Audio Devices Hider, Astra Monitor; Tiling Assistant is only enabled) with `gext` from mise. Their shared settings (`home/gnome/.config/machine/dconf/*.ini`) are loaded once per host; delete `~/.local/state/machine/gnome-extension-settings` to load them again. Log out and in afterwards. Host-specific keys (audio device names, Astra storage device) are not shipped. Ddterm is the drop-down terminal (F12); with the feature `fonts`, `machine` sets its font, like the VS Code terminal's, to FiraCode Nerd Font Mono and keeps the size. Guake is no longer installed or configured; an installed Guake is left alone (`sudo apt remove guake` removes it).

Feature `touch-device`: `machine` installs and enables the GNOME Shell extensions TouchUp and Screen Rotate without root, with the same `gext` from mise (dotfile group `gnome-extensions`, shared with `gnome`), also on hosts without the feature `gnome`. Log out and in after a new install. Details: [thinkpad-l13-yoga-gen2.md](thinkpad-l13-yoga-gen2.md#touch-extensions-feature-touch-device).

Yoga/convertible (L13): feature `stylus-touch-guard` → role `stylus_touch_guard`. Previously: [helpers-and-automation](https://github.com/ditschi/helpers-and-automation) (**archived / deprecated**).
Laptops: features `lid-switch` (closing the lid does nothing), `power-profile-switch` and `battery-charge-limit` (`battery-charge status|normal|full`) are preselected on desktops and applied only on detected laptops; `zram-swap` is preselected everywhere except containers and not applied on Raspberry Pis. Tuning for one model is a role selected by the hardware, not a feature: `thinkpad_l13_yoga_gen2` (S3 suspend, tablet on-screen keyboard), see [docs/thinkpad-l13-yoga-gen2.md](thinkpad-l13-yoga-gen2.md). Fingerprint login is set up by hand, not by `machine`: [docs/fingerprint.md](fingerprint.md). `MACHINE_HARDWARE` also accepts `l13-yoga-gen2` in tests.
Memory headroom: feature `memory-headroom` (default on private desktops, optional on work desktops, never on servers or in containers, not applied on Raspberry Pis) lets the session get slower before anything is killed. The role `memory_headroom` grows the swap file on disk to the RAM size plus 2 GiB (`memory_headroom_swapfile_size_gib`, 16 GiB on the L13; never shrunk, used after zram, skipped with a warning on btrfs, when less than 20 GiB and 5 % of the disk would remain free, or when too little RAM is free to turn the swap file off for a moment; the warning shows the commands to do it by hand, and the next run tries again), raises the systemd-oomd memory pressure limit of user sessions from Ubuntu's 50 % to 80 % (`/etc/systemd/system/user@.service.d/90-oomd-limit.conf`) and turns off swap-based systemd-oomd kills (`/etc/systemd/system/-.slice.d/90-oomd-no-swap-kill.conf`, Ubuntu's default anyway). The dotfile group `memory-headroom` gives every scope of the Claude desktop app `MemoryHigh=8G` (its memory goes to swap first) and `OOMPolicy=continue` (a kernel OOM kill of one process, for example a test run started by Claude Code, no longer ends the whole app); both apply from the app's next start. Check: `swapon --show`, `systemctl show user@$(id -u).service -p ManagedOOMMemoryPressureLimit`, `systemctl show -- -.slice -p ManagedOOMSwap`, `systemctl --user show 'app-*Claude*' -p MemoryHigh -p OOMPolicy`, `journalctl -k | grep -i 'out of memory'`. Deselecting removes nothing: delete the two drop-ins under `/etc/systemd/system/` and run `sudo systemctl daemon-reload`; to shrink the swap file, `sudo swapoff /swap.img`, recreate it (`sudo rm /swap.img && sudo fallocate -l 4G /swap.img && sudo chmod 600 /swap.img && sudo mkswap /swap.img`) and `sudo swapon /swap.img`. See [ansible/roles/memory_headroom/README.md](../ansible/roles/memory_headroom/README.md).
COSMIC: feature `cosmic` (optional on desktops, never on servers or in containers) installs `cosmic-session` on Ubuntu 26.04+ from the unofficial PPA `ppa:hepp3n/cosmic-epoch` (key pinned in the role); GDM stays the display manager, so GNOME and COSMIC can both be chosen at login. Pop!_OS ships COSMIC, so nothing happens there. The feature also selects the dotfile group `cosmic`, whose user unit removes `DCONF_PROFILE` before a GNOME session starts: COSMIC puts it into the systemd user manager, and with linger it would otherwise survive the logout and make the next GNOME login use COSMIC's dconf database. Deselecting removes nothing; see [ansible/roles/cosmic_desktop/README.md](../ansible/roles/cosmic_desktop/README.md).
Syncthing: feature `syncthing` (default on private desktops, optional on servers, never for work or in containers) installs Syncthing and keeps build output out of every shared folder. The shared rules live in a synced file `.stglobalignore` at the root of each folder; each device's own `.stignore` loads it with `#include .stglobalignore` as its first line, then `!/.stglobalignore` (so that the shared file stays synced in a folder whose own lines are an allow list ending in `*`), followed by the device's own lines. The step `syncthing ignores` of `machine setup`, `apply` and `update` works on the login user's Syncthing (configuration from `syncthing paths`): it adds the two lines to every folder that has `.stglobalignore` (only `!/.stglobalignore` to one that has not); for a folder without one it creates the file from [`machine/syncthing/stglobalignore`](../machine/syncthing/stglobalignore) only when no device known to Syncthing has announced one (otherwise, or with Syncthing stopped or the folder paused, the folder is reported as waiting, because an include of a missing file puts the folder into an error state). It never changes an existing `.stglobalignore`, deletes a Syncthing conflict copy of it only when the content is the same and reports any other one, and sets Syncthing's default ignore patterns to the shared rules followed by the host's own default lines (such as `__*`). To sync something the rules ignore, add `!<path>` above the rules in the folder's `.stglobalignore`; it applies on every device. A `.stglobalignore` made before this change (as on "ALL Documents") does not get new rules from the repository: add them by hand, today `(?d)@eaDir`, `(?d)#recycle`, `(?d)#snapshot` and `**/.claude/worktrees`. Devices without the dotfiles (NAS, phone, Raspberry Pi, family laptops) are set up once by hand: put `!/.stglobalignore` into each folder's ignore patterns in the Syncthing GUI and, only after `.stglobalignore` has arrived in that folder, `#include .stglobalignore` above it as the first line.
Mail: feature `thunderbird` (default on private desktops) installs Thunderbird and the mise group `home/thunderbird` with `tb` and `tb-bridge` of [thunderbird-cli](https://github.com/vitalio-sh/thunderbird-cli). The bridge extension is not installed automatically, because it accepts any local bridge, also one of another user: `machine` downloads the pinned XPI to `downloads/` in the checkout (gitignored); install it once in Thunderbird (Add-ons and Themes → gear → Install Add-on From File). Start the bridge with `tb-bridge &`, then `tb health`.

## Homelab Compose host (feature `homelab-node`)

Optional on private servers. Prepares a host of the [homelab repository](https://github.com/ditschi/homelab) so that its Docker Compose stacks run straight from a git clone and CI deploys with `ssh <host> homelab deploy <sha>` (homelab `docs/compose-gitops.md`, "Keys" and "Host layout"). The role `homelab_node` sets up, for one deploy user:

- **Deploy user**: `homelab.user` in the host config; otherwise the user who runs `machine`, or `ditschi` when `machine` runs as root. Root is never the deploy user. A missing user is created with a locked password, key login only and no sudo; existing users keep password, shell and groups. The user gets the `docker` group (the Docker engine itself is not touched) and, in `authorized_keys`, the keys of `ssh_allow_from` (so `ssh ditschi@<host>` and `ssh -A` for pushing work) and the CI key `machine/ssh_keys/homelab-ci.pub`.
- **CI key**: added only with `restrict,command="/usr/local/bin/homelab-ci"`; the wrapper runs nothing but `homelab deploy <sha>`. An entry that already exists (contabo, oracle, used by today's rsync deploy) keeps its options until the host config sets `homelab.ci_restrict: true`, which you do once CI uses `homelab deploy`; until then `machine attention` reminds you.
- **Clone**: `/opt/homelab` on branch `main`, owned by the deploy user, fetched with a per-host read-only deploy key `~/.ssh/homelab_deploy_ed25519` that only this clone uses (`core.sshCommand`; GitHub's host keys are pinned in `/etc/ssh/homelab_github_known_hosts`). Without an agent only the deploy key is offered, so fetching works and pushing does not; with `ssh -A` your forwarded key comes first and pushing works. An existing clone is never fetched, reset or switched. `homelab.clone` with another path (homeserver: `/mnt/data-internal/homelab`) is an existing checkout: used as it is, no clone, no deploy key.
- **sops** 3.13.3 from the GitHub release, sha256-checked, in `/usr/local/bin/sops`. When another `sops` comes first in a non-interactive SSH session of the deploy user (for example a mise shim without a version), `machine attention` names it; the role removes nothing.
- **Age key**: the host key from the Bitwarden item `homelab-age-<host>` (see [secrets.md](secrets.md)) in `~/.config/sops/age/keys.txt` (mode 600), written only when the file is missing or holds no key. A file with another key is kept and reported. The personal key never goes onto a server.
- **CLI**: `/usr/local/bin/homelab` and `/usr/local/bin/hl` link to `<clone>/scripts/homelab.py`, so they work in non-interactive SSH sessions; git, python3 and PyYAML come from apt. The homelab CLI and sops ship no Bash or Zsh completion.

The role never starts, stops, restarts or prunes containers, never reboots and never reads or writes the data root (contabo runs GuardedSleep). What it could not finish goes into `/var/lib/machine/homelab-node.json`, which `machine attention` reads.

First run on a host (also a new VM that only has `root`: bootstrap the dotfiles as root with `homelab-node` in its host config):

1. `machine apply` prints the new deploy key.
2. Add it under github.com/ditschi/homelab → Settings → Deploy keys, write access off.
3. `machine apply` again: the clone follows. `machine attention` shows what is still open.

Deselecting the feature removes nothing: delete `/opt/homelab`, `~/.ssh/homelab_deploy_ed25519*`, `/usr/local/bin/{homelab,hl,homelab-ci}` and the user by hand if wanted. Details: [ansible/roles/homelab_node/README.md](../ansible/roles/homelab_node/README.md).

SSH home fleet: feature `sshd-home` → `authorized_keys` (`roles/sshd_home`) from [`machine/ssh_keys/`](../machine/ssh_keys/) for entries in `ssh_allow_from`.

## Kerberos ticket (work, feature `kerberos`)

The proxy needs a valid Kerberos ticket. On hosts with the feature `kerberos`, the user timer `work-net-kerberos.timer` runs `work-net kerberos refresh --auto` one minute after boot and every 10 minutes, also without a login (linger). It does nothing while the ticket is valid for more than 2 hours, renews it without a password (`kinit -R`) shortly before it expires, and requests a new one with the password only when the ticket is missing or can no longer be renewed and the KDC is reachable. Shell start does not touch the ticket.

- **Password:** `get-password` returns `PASSWORD` from `~/.env`, `~/.env.host`, `~/.env.local` (also in services without the shell environment). Only without it does it read the GNOME keyring, and only when the keyring is unlocked, so no unlock dialog appears. The refresh keeps the keyring entry equal to the env password while the keyring is unlocked.
- **Failure guard:** a rejected password counts; network errors and timeouts do not. After 2 rejections at least 15 minutes apart, or at once when the account is locked or the password has expired, automatic logins stop and a desktop notification says why. Fix `PASSWORD` in `~/.env` (for example with `machine env pull`), then run `kinit-pw` in a terminal: that resets the guard. A changed password also resets it.
- **Check and debug:** `work-net status` shows the ticket, the KDC, the guard and the last action; `work-net -v kerberos refresh` (or `WORK_NET_DEBUG=1`) logs every step. To try the renewal now, raise the threshold for one run: `WORK_NET_RENEW_BEFORE_HOURS=12 work-net -v kerberos refresh`. Logs: `~/.local/state/work-net/work-net.log` (the journal is not readable for AD users without the `systemd-journal` group). Stop the timer with `systemctl --user disable --now work-net-kerberos.timer`.
- Timeouts: `kinit` 30 s, keyring 5 s, KDC check 2 s. `work-net` has no Bash or Zsh completion.

## Work VPN (work desktops with the OSD VPN tool)

On a work desktop with `/usr/bin/osd-vpn-connect`, the user service `work-net-vpn-watch.service` runs `work-net vpn watch` while you are logged in to the desktop. It reacts to login, wake from sleep and network changes (and checks every 2 minutes):

- Kerberos server reachable (office LAN, USB-LAN, work Wi-Fi or VPN already up): no VPN start, only the Kerberos refresh.
- No network: waits for the next event.
- VPN client still running or a connect in progress: waits up to 45 s for its own reconnect, which is faster than a new connect; it checks every 5 s and connects at once if the client gave up.
- Otherwise it connects with `sudo -n /opt/osd/osd-wifivpn-package/connect_vpn.sh` (passwordless by the corporate sudoers) and the password from `get-password`. Before each connect it sets `USE_KEYRING=0` in `~/.wifivpn/vpn_preferences.ini`: the OSD script then uses the password from its input instead of its own keyring copy, which would be used even when stale and asks for unlocking a locked keyring. A certificate warning does not block; under 20 days a desktop notification says to run `osd-wifivpn-enroll` in the office.

Logging out stops the watcher but leaves the VPN connected, so running agents and tasks keep working. Connect attempts use the same failure guard as Kerberos; an unreachable gateway, a timeout (120 s) or a missing sudo rule are not counted.

| Command | Effect |
| --- | --- |
| `vpn-pw` / `osd-vpn-connect-pw` | `work-net vpn connect`: connect now with the env password; resets the failure guard and ends a pause |
| `osd-vpn-disconnect` | `work-net vpn disconnect`: disconnect and pause the watcher until the next login or wake |
| `work-net vpn check --dry-run` | print what the watcher would do now and why |
| `work-net status` | ticket, KDC, guard, VPN client, pause, certificate days, last action |
| `less ~/.local/state/work-net/work-net.log` | the watcher's decisions and the OSD script's output (never the password); capped at 1 MiB plus one old file |
| `systemctl --user stop work-net-vpn-watch` | stop the watcher for this session (`disable --now` permanently) |

If a connect hangs: `sudo -n /opt/osd/osd-wifivpn-package/disconnect_vpn.sh`, then `vpn-pw`. `/usr/bin/osd-vpn-connect` and `/usr/bin/osd-vpn-disconnect` by full path are the unchanged OSD tools; the watcher treats a disconnect by full path as a drop and reconnects. `osd-vpn-connect` without the pipe now asks for the password, because its keyring use is switched off; `osd-vpn-connect -k` uses the keyring copy for that run.

Working Azure CLI and GitHub CLI installations are kept, including their
authentication and package sources. Docker provisioning preserves an existing
provider instead of replacing it with `docker.io`; only a missing,
provider-compatible Compose package is added. Unmanaged providers may need
manual Compose setup. Work hosts do not preselect Docker.
