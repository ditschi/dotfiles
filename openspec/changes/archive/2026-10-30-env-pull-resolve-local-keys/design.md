# Design

## Context

`cmd_env_pull` in `machine_cli/env_pull.py` builds `~/.env` from the group item (`env/groups/<group>`; each context has exactly one group) and `~/.env.host` from `env/hosts/<host>`. Each item becomes a section `# --- <item> ---` below a header `# generated by machine env pull — do not commit`. Item content is the item's notes followed by its custom fields as `NAME=value`.

Before writing, it compares the keys of each existing file with the generated keys and `~/.env.local`. Missing keys are moved into `~/.env.local` automatically if that file does not exist; otherwise, or when a file contains shell code, it calls `die()`. `machine update` calls `cmd_env_pull()` before `check_ssh_key_backup()` and the update-state write, so a `die()` skips both. The background job (`machine update --auto`) does not run the env sync, so it cannot revert because of it.

Interactivity elsewhere in `machine` is `system.is_tty() and not self.unattended` (`--yes` sets `unattended`); prompts use `system.choose`. `machine attention` builds its items live (`attention_items()` in `machine_cli/attention.py`), without a stored list.

## Goals / Non-Goals

**Goals:**
- One decision per local-only key, made by the user, on the spot or later via `machine attention`.
- The env sync always finishes; Bitwarden values always arrive for files without shell code.

**Non-Goals:**
- Changing the storage format of env items (notes stay the format; see Decisions).
- Running the env sync in the background job.
- Detecting keys that `~/.env.local` sets but Bitwarden also sets (overrides stay the user's business).

## Decisions

**Carry local-only keys over inside the generated file.** Unresolved keys go, unchanged, into a section at the end of the generated file:
`# --- local only: not in Bitwarden (resolve with machine attention) ---`.
The shell keeps the key, Bitwarden updates still arrive, and `~/.env.local` is not touched. Rejected: leaving the whole file unchanged (Bitwarden changes would not arrive until the user acts); dropping the key and relying on the backup (the key would silently vanish from the shell); moving it into `~/.env.local` automatically (the user decides every move).

**The user decides every move, also without a terminal.** The automatic move into a new `~/.env.local` is removed. Without a terminal or with `--yes`, every local-only key is carried over and listed by `machine attention`. Rejected: keeping the automatic move for non-interactive runs, because two paths for the same situation are harder to predict.

**The Bitwarden target follows from the file.** `~/.env` maps to `env/groups/<group>`, `~/.env.host` to `env/hosts/<host>`; there is one group per context, so no second question is needed. The prompt names the item so the user sees that a group key reaches every host of the context; "keep locally" is the choice for a host-only value in `~/.env`.

**"Add to Bitwarden" appends to the notes.** Notes are the existing format of env items. The original line is appended under `# added from <host> on <YYYY-MM-DD>`, keeping `export`, quoting and order. Rejected: hidden custom fields. They are masked only in the web vault form, `bw get item` returns them in clear like notes, and they lose comments and order; switching all items would be a separate change. Keys chosen for the same item are written in one `bw edit item`; the item is read with `bw_get_item_raw` right after `bw sync` and written with `bw_edit_item`. After a successful write the sync runs again and regenerates the files, so the key comes from the vault. If unlocking or writing fails, the keys are treated as skipped.

**Skip is preselected; the origin is a hint.** Every prompt preselects "skip", so pressing Enter never moves or deletes anything. Rejected: preselecting by origin (Bitwarden for hand-written or local-only keys, remove for keys deleted in the vault), because an accidental Enter would then write to the vault or drop a key. A key that a generated file had in a `# --- <item> ---` section, but that the item no longer sets, is shown with "(was in <item>; deleted there?)"; when it is carried over, a `# was in <item>` comment above it keeps that origin for later prompts.

**Shell code keeps the whole file.** Lines that are neither comments nor `KEY=value`/`export KEY=value` (or assignments `shlex` cannot parse) cannot be carried over safely. That file is left unchanged (after the usual backup); the other file is still generated. Its choices are keep locally (append the lines to `~/.env.local`), remove, or skip.

**A key counts as sourced if either generated file sets it.** A key that moved from the group item to the host item is not local-only in `~/.env`; this keeps the existing migration from the old combined `~/.env` working.

**A missing item is created.** If the item of the file does not exist yet (typically `env/hosts/<host>`), "add to Bitwarden" creates it as a secure note holding the lines.

**Attention items are derived from the files.** The env item exists while a generated env file has a local-only section, or an env file holds shell code. No state file is kept; resolving through the item runs the same resolution code as the sync and then the sync itself.

**No abort, short notice.** `cmd_env_pull` no longer calls `die()` for local-only content and returns normally, so `machine update` and `machine setup` continue. It prints one notice per file: keys, file, item, backup path, and `run: machine attention`. Prompts and notices show key names only, never values.

**`~/.env.local` is only appended to.** "Keep locally" appends the line under `# kept from ~/.env on <YYYY-MM-DD>`, creating the file with mode `600` if missing. Existing content is never rewritten.

## Risks / Trade-offs

- [A group key added to Bitwarden reaches all hosts of the context] → the prompt names `env/groups/<group>`; "keep locally" stays available.
- [`bw edit item` overwrites the notes with what was read] → read the item right after `bw sync` and edit immediately; a concurrent edit elsewhere in that window is accepted as unlikely for a single owner.
- [A generated file keeps a local-only section for a long time] → the attention item stays until resolved; the notice on each manual sync repeats it.
- [Behaviour change for hosts that relied on the automatic move] → their keys now stay in the local-only section and remain set; nothing is lost.

## Migration Plan

No migration step. On the first sync after the change, keys that today block the sync land in the local-only section (or in the prompt). Rollback: revert the commit; files with a local-only section are then treated like hand-edited generated files by the old code, which blocks as before without data loss.

## Open Questions
