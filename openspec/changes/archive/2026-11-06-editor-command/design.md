# Design

## Context

See proposal.md for the motivation and specs/editor-command/spec.md for the required behaviour.

Relevant repository structure:

- The feature table `ansible/group_vars/all/features.yml` is the single source for feature help, dotfile groups and defaults. A feature with its own group needs no change to the `machine` CLI (spec `feature-selection`).
- Dotfile groups under `home/<group>/` are linked file by file into `$HOME` by `mise`. A group that is no longer selected loses its links on the next apply. Two groups with the same target are a conflict (spec `repo-layout`). The repository currently contains no symbolic links inside groups.
- Small user scripts live in `home/<group>/.local/bin/` (for example `home/core/.local/bin/get-password`, bash, and `ssh-route`, Python). Scripts are tested with stub commands on `PATH` (for example `tests/unit/test_laptop_scripts.py`).
- `claude-code` selects the groups `claude` and `openspec`, and `copilot-cli` selects `copilot` and `openspec`. Today these groups contain only `mise` fragments. Agent instructions for this repository (`.claude/skills/openspec-*`, `.github/skills/openspec-*`) are generated by `openspec` and are not user-level.
- `$EDITOR` is `nano` (`home/core/.shell/common/environment.sh`). On the owner's laptop, `code` (snap) and `cursor` are installed.
- Branch and worktree names of OpenSpec changes are equal to the change name (AGENTS.md: `git worktree add "$(machine repo)/.worktrees/<change-name>" -b <change-name>`).

## Goals / Non-Goals

**Goals:**
- One `/editor` command with the same behaviour in Claude Code, Copilot CLI, VS Code Copilot Chat and opencode, in every repository on a host with the feature.
- The deterministic parts (work root, editor choice, change lookup, start of the editor) live in a script that can be tested without an agent. The agent only picks files from a hint.

**Non-Goals:**
- Installing editors.
- Changing `$EDITOR`/`$VISUAL` or Git's `core.editor`.
- Opening files on another host than the one the agent runs on, except where the editor's own command already does that (VS Code Remote terminals).

## Decisions

1. **A dotfiles feature with its own group, `editor-command`.** It works for every repository and every agent at once and follows the feature table like other features. Its values are preselected on desktops, optional on servers (where VS Code Remote-SSH provides `code` in its terminal) and excluded in containers.
2. **The preferred editor is the Git configuration key `editor.open`, default `code`.** A per-repository value lives in `.git/config` and is never committed. A host default can be set globally, for example in `~/.gitconfig.local`. Git's normal precedence makes the repository value win. In a linked worktree, Git reads the main repository's `.git/config`, so worktrees follow their repository. This was preferred over an environment variable, which cannot be set per repository without extra tooling, and over a committed file in the repository, which would impose the owner's editor on everyone who clones it.
3. **The agent resolves hints, a script opens.** The agent has the conversation and can search, so it is best placed to tell which file `editor.md` means. The script does everything that can be decided without the conversation, so that this part behaves the same in every agent and is unit-tested. A script-only fuzzy match was rejected because it cannot use the conversation.
4. **One skill named `editor` in the Agent Skills format, plus an opencode command (owner decision, 2026-11-06).** Claude Code, Copilot CLI and VS Code Copilot Chat all load personal skills from a `SKILL.md` with `name` and `description` front matter (see Verified facts). The skill is user-invoked only (`disable-model-invocation: true` in Claude Code), takes an optional argument and allows only the `open-in-editor` command. opencode offers user slash commands as Markdown files in `~/.config/opencode/commands/`, so it gets a command file with the same body and its own front matter. One file in the repository is the source of the skill. The Copilot target `.copilot/skills/editor/SKILL.md` is a relative symbolic link to it inside the group, which `mise dot apply` links like any other file (task 1.2). The opencode body is checked by a test to be equal to the skill body. All targets are installed with the group, whichever agents are installed, because an instruction file of an agent that is not installed has no effect.
5. **The work root is the Git worktree top level.** In an agent session inside `.worktrees/<change>`, the worktree opens, not the main checkout. Outside Git, the current directory opens.
6. **`--change` opens proposal, design, tasks and the delta specs (owner decision, 2026-11-06).** The delta specs follow the three planning files, sorted by path. The current change is the one named like the branch, otherwise the only active one. Exit status 2 with the list of active changes tells the agent to ask the user.
7. **Missing files and a missing editor are reported, not guessed around.** The script never falls back to another editor than the configured one. That would hide a typo in `editor.open`.

## Implementation outline

- **Feature row** in `features.yml`:
  ```yaml
  editor-command:
    help: /editor in Claude Code and Copilot opens the work dir in your editor
    groups: [editor-command]
    server: optional
    container: excluded
  ```
- **Group entry** `[dotfile_groups.editor-command]` with `root = "home/editor-command"` in `mise.toml`, like the other groups.
- **Script** `home/editor-command/.local/bin/open-in-editor` (bash, `set -euo pipefail`):
  1. Parse `[--change [NAME]] [--] [FILE...]`.
  2. Work root: `git rev-parse --show-toplevel` in the current directory, or `$PWD` on failure.
  3. Editor: `git -C <root> config --get editor.open`, or `code`. Split the value into words. When `command -v` does not find the first word, exit 1 with a message naming the command and `editor.open`.
  4. Files: make every given path absolute against `$PWD`. Report and drop the missing ones, and remember to exit 1 at the end.
  5. `--change`: list active changes as the directories in `<root>/openspec/changes/` except `archive`. Without a name, use `git -C <root> branch --show-current` if that directory exists, else the only active change, else print the list and exit 2. An unknown name prints the list and exits 1. Append the existing `proposal.md`, `design.md` and `tasks.md`, then `specs/**/spec.md` of the change sorted by path.
  6. Start `<editor words> <root> <files...>` detached (`setsid`, output to `/dev/null`, `stdin` from `/dev/null`) so that the agent's command returns at once, then print the editor command and the opened paths on one line each.
- **Skill** `home/editor-command/.claude/skills/editor/SKILL.md` and the Copilot target `home/editor-command/.copilot/skills/editor/SKILL.md`:
  - front matter: `name: editor`, `description` ("Open the current work directory, and optionally files from a hint or an OpenSpec change, in the preferred editor. Use only when the user runs /editor."), `argument-hint: [file hint | change [name]]`, `disable-model-invocation: true`, `allowed-tools: Bash(open-in-editor:*)`.
  - opencode target `home/editor-command/.config/opencode/commands/editor.md`: front matter `description` only, the same body, with the argument taken from `$ARGUMENTS`.
  - body: the three cases of the spec (no argument, `change [NAME]`, hint), the rule to ask with numbered options when unsure or on exit 2, the rule to never edit files, and to report the script's output in one line.
- **Completion:** `open-in-editor` provides no bash or zsh completion. Default file-name completion covers its file arguments. No completion is added.
- **Docs:** a section `## Open the work directory in an editor (/editor)` in `docs/tools.md` with usage, `git config editor.open cursor` per repository, the global default, and the `change` argument.

## Testing

- `tests/unit/test_features.py`: values of `editor-command` per context and device, and its group.
- `tests/unit/test_open_in_editor.py`, run against temporary Git repositories with a stub editor on `PATH` that records its arguments:
  - work root at the top level of the main checkout, of a linked worktree, and outside Git;
  - `editor.open` unset, set globally (`GIT_CONFIG_GLOBAL` pointing to a temporary file), set per repository over a global value, and set with an argument;
  - configured editor missing: non-zero exit, message, stub not called;
  - relative and absolute files, and a missing file;
  - `--change` with a name (planning files and delta specs in the specified order), an unknown name, a branch match among several changes, a single active change, an archived change that does not count, and several changes without a match (exit 2, list printed);
  - the script returns while the stub editor is still running.
- A test that the group contains the skill for both targets with the same content, valid front matter (`name`, `description`) and `allowed-tools` limited to `open-in-editor`, and an opencode command whose body equals the skill body.

## Risks / Trade-offs

- [VS Code Copilot Chat reads both `~/.copilot/skills` and `~/.claude/skills`, so it sees the skill `editor` twice.] → Both copies are the same file. Copilot CLI reads only `~/.copilot/skills` or `~/.agents/skills` (VS Code reads both of those too), so no target avoids the duplicate. Task 4.3 checks how VS Code shows it.
- [Copilot CLI is not installed on the owner's laptop (feature `copilot-cli` is optional on private hosts), so its `/editor` cannot be tried there.] → Its skill locations and `/<name>` invocation are taken from GitHub's documentation. It is checked by hand on the first host with `copilot-cli`.
- [Copilot does not know Claude Code's `allowed-tools` syntax (`Bash(open-in-editor:*)`) or `disable-model-invocation`.] → Copilot then asks before running the command, which is acceptable. The skill text itself also says to run only on `/editor`.
- [The opencode command can drift from the skill.] → A test checks that its body equals the skill body.
- [On a server reached by plain SSH, `code` is not on `PATH`.] → The script reports the missing command. The feature is only optional on servers.
- [A detached GUI start from an agent without a graphical session (no `DISPLAY` or `WAYLAND_DISPLAY`) silently opens nothing.] → The script prints the command it started. Diagnosing GUI sessions is left to the editor.
- [The `editor.open` key could clash with a future Git key.] → Git has no `editor` section today. The key name is easy to change before archive.

## Verified facts

Checked on 2026-11-06 on ThinkPad-L13-Yoga-Gen-2 (task 1.1 and 1.2):

- Claude Code 2.1.308 loads a personal skill from `~/.claude/skills/<name>/SKILL.md` with `disable-model-invocation: true`, runs it as `/<name> <argument>` and replaces `$ARGUMENTS` with the argument (probe skill run through `claude -p`).
- opencode 2.1.4 loads commands from `{command,commands}/**/*.md` below its configuration directories, follows symbolic links, names the command after the file, and replaces `$ARGUMENTS`, `$1`, ... with the arguments (read from the installed binary; a live run failed at the configured model provider, not at the command).
- Copilot CLI reads personal skills from `~/.copilot/skills` or `~/.agents/skills` and runs a skill as `/<name>`; front matter `name`, `description`, `license` and `allowed-tools` (GitHub documentation "Creating agent skills for GitHub Copilot CLI"). It does not list `~/.claude/skills`.
- VS Code Copilot Chat reads personal skills from `~/.copilot/skills`, `~/.claude/skills` and `~/.agents/skills`, offers them as `/<name>` with text after it, and supports `argument-hint` and `disable-model-invocation` (VS Code documentation "Agent Skills").
- `code` (VS Code 1.145.0) and `cursor` (3.22.12) both take `[options] [paths...]`, so the work root and the files are passed in one call.
- `mise dot apply` (mise 2026.10.15) links a group file that is itself a relative symbolic link inside the repository; the target in the home directory then resolves to the link's source file (scratch repository and home under the session scratchpad).

## Assumptions

- `code <dir> <file>...` and `cursor <dir> <file>...` open the files in the window of that folder and reuse a window that already has the folder open (their documented default; checked by hand in task 4.3).
