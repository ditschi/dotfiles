## MODIFIED Requirements

### Requirement: Generated and local files
`~/.env` (group and profile items) and `~/.env.host` (host item) SHALL be generated by `machine env pull` from Bitwarden (`env/groups/<group>`, `env/hosts/<hostname>`), and previous contents SHALL be backed up. `~/.env.local` SHALL be local-only. It SHALL never be overwritten, and SHALL be changed only by appending lines the user chose to keep locally.

#### Scenario: Pulling env files
- **WHEN** a user runs `machine env pull`, no local-only key is chosen to be kept locally and neither generated file has unpushed local edits
- **THEN** `~/.env` and `~/.env.host` are rewritten from Bitwarden after a backup, and `~/.env.local` is untouched

#### Scenario: Keeping a key locally
- **WHEN** the user picks "keep locally" for a local-only key
- **THEN** its line is appended to `~/.env.local` and the existing content of `~/.env.local` is unchanged

### Requirement: Shell code in an env file
When an existing `~/.env` or `~/.env.host` holds lines that are neither comments nor assignments, the sync SHALL leave that file unchanged and record an attention item. Its choices SHALL be keep locally, remove or skip; there is no Bitwarden choice.

#### Scenario: Conditional block
- **WHEN** `~/.env.host` contains an `if … fi` block
- **THEN** `~/.env.host` is unchanged, the other env file is still generated and an attention item names `~/.env.host`

#### Scenario: Quote in a plain file
- **WHEN** `~/.env` has no `export` line and contains `PASS=it's a b`
- **THEN** the line is an assignment, as the shell loader reads it, and not shell code

## ADDED Requirements

### Requirement: References to other Bitwarden items
A value in an `env/…` item, in its notes or a custom field, of the form `{{bw:<item name>/<target>}}` SHALL be a reference; `<target>` is `password`, `username` or `field:<NAME>`, and the item name is matched exactly. `machine env pull` SHALL write the referenced value so that the shell loader reads it unchanged, after a comment that names the item and the target, and SHALL never write the reference text itself.

#### Scenario: Password reference
- **WHEN** the notes of `env/groups/work` contain `PASSWORD={{bw:Work login/password}}` and the login item `Work login` exists once
- **THEN** `~/.env` sets `PASSWORD` to that item's login password after the comment `# PASSWORD from Bitwarden "Work login" (password)`

#### Scenario: Custom field reference
- **WHEN** a note line is `TOKEN={{bw:CI/field:api-token}}` and the item `CI` has a custom field `api-token`
- **THEN** `~/.env` sets `TOKEN` to that field's value

#### Scenario: Value with quotes and spaces
- **WHEN** the referenced password contains spaces, quotes and `$`
- **THEN** the shell loader sets exactly that password, whether the file is sourced (it has `export` lines) or parsed as plain `KEY=value`

#### Scenario: Similar names
- **WHEN** a reference names `Work login` and Bitwarden holds only `Work login old`
- **THEN** the reference is not resolved

### Requirement: Unresolved reference
When a reference cannot be resolved, because the item is missing or not unique, the target is missing or empty, or the value has a line break or `${`, which the loader would change, the pull SHALL keep the key's value from the last pull, or leave the key out when there is none, SHALL warn with the key and the item but never a value, and SHALL record an attention item.

#### Scenario: Referenced item deleted
- **WHEN** `~/.env` sets `PASSWORD` from a reference and the referenced item no longer exists
- **THEN** the pull keeps the previous `PASSWORD` value, warns naming `PASSWORD` and the item, and `machine attention` lists it

#### Scenario: Local edit while unresolved
- **WHEN** the user changed a referenced key in `~/.env` and the reference cannot be resolved at the next pull
- **THEN** the edit stays an unpushed local edit and is not taken as the key's pulled value

#### Scenario: Two items with the name
- **WHEN** two items carry the referenced name
- **THEN** the key is not resolved from either of them and an attention item names the item

### Requirement: Syntax hint in generated files
The header of a generated `~/.env` and `~/.env.host` SHALL contain a short comment that shows the reference syntax with its targets and names `machine env push` as the way to write edits back to Bitwarden.

#### Scenario: Fresh pull
- **WHEN** `machine env pull` writes `~/.env`
- **THEN** its header shows `{{bw:<item name>/password}}`, `/username` and `/field:<NAME>` and names `machine env push`

### Requirement: Unpushed local edits
The pull SHALL remember, owner-readable only, the content it last wrote for each generated file. A key that this content set from a Bitwarden item and whose line the file now changes or lacks is an unpushed local edit. Keys added to the file stay local-only keys.

#### Scenario: Changed value
- **WHEN** the user changes the value of `PASSWORD` in `~/.env` after the last pull
- **THEN** the next pull treats `PASSWORD` as an unpushed local edit

#### Scenario: Added key
- **WHEN** the user adds a key that no item sets to `~/.env`
- **THEN** the next pull handles it as a local-only key, not as an unpushed local edit

### Requirement: Unpushed local edits in a terminal
On a terminal and without `--yes`, the pull SHALL ask once per file with unpushed local edits, by number: push the edits now, discard them, or skip; "skip" is preselected. Discard SHALL regenerate the file after a backup; skip SHALL leave the file unchanged and record an attention item.

#### Scenario: Discard
- **WHEN** the user picks "discard" for `~/.env`
- **THEN** `~/.env` is regenerated from Bitwarden and the backup holds the edited file

#### Scenario: Push from the pull
- **WHEN** the user picks "push the edits now"
- **THEN** the pull runs the push for that file and regenerates it afterwards

### Requirement: Unpushed local edits without a terminal
Without a terminal or with `--yes`, the pull SHALL leave a file with unpushed local edits unchanged, still generate the other file, and record an attention item that offers push or discard.

#### Scenario: Background update
- **WHEN** the background update pulls while `~/.env` has an unpushed local edit
- **THEN** `~/.env` is unchanged, `~/.env.host` is generated and `machine attention` offers push or discard for `~/.env`

### Requirement: Push command
`machine env push` SHALL write `~/.env` to `env/groups/<group>`, and with `--host` `~/.env.host` to `env/hosts/<hostname>`, taking only the keys the file adds, changes or removes relative to the last generated content. It SHALL list them by name, show references in clear and never show values, write nothing before the user confirms, and then sync and regenerate the file. A file with shell code SHALL be refused.

#### Scenario: Added reference
- **WHEN** `~/.env` has the new line `SONAR_TOKEN={{bw:Sonar/password}}` and the user runs `machine env push` and confirms
- **THEN** the notes of `env/groups/<group>` contain that line and the regenerated `~/.env` sets `SONAR_TOKEN` to the resolved value

#### Scenario: Changed reference
- **WHEN** the user replaces the `PASSWORD` line in `~/.env` with a reference to another item and pushes
- **THEN** the `PASSWORD` line in the item's notes is replaced by the new reference

#### Scenario: Not confirmed
- **WHEN** the user declines the confirmation
- **THEN** Bitwarden and the file are unchanged

### Requirement: Push checks references
Before writing, the push SHALL check that every added or changed reference names exactly one item that has the target. If one does not, the push SHALL write nothing and SHALL name the key and the reason.

#### Scenario: Typo in the item name
- **WHEN** an added reference names an item that does not exist
- **THEN** the push writes nothing and names the key and the missing item

### Requirement: Push of a new value for a referenced key
When a key that the item sets from a reference has a new literal value in the file, the push SHALL write that value into the target field of the referenced item, and the note SHALL keep the reference.

#### Scenario: New work password
- **WHEN** `PASSWORD` comes from `{{bw:Work login/password}}`, the user types a new value for `PASSWORD` into `~/.env` and pushes
- **THEN** the login password of `Work login` is the new value and the note still holds the reference

### Requirement: Push of removed keys
For each key that the file lacks but the item sets, the push SHALL ask whether to remove it from the item, with "no" preselected. A declined removal SHALL leave the item unchanged, so the following pull writes the key again.

#### Scenario: Confirming the default
- **WHEN** a key is missing from `~/.env` and the user presses Enter at the removal question
- **THEN** the key stays in the item and the regenerated `~/.env` sets it again

### Requirement: Push conflicts
When the item changed a key since the last pull and the file changes the same key to a different value, the push SHALL show the key as a conflict and write it only after a separate confirmation, with "no" preselected. When both sides hold the same new value, there is no conflict and nothing is written. Keys that only Bitwarden changed SHALL NOT be written back.

#### Scenario: Changed in the vault only
- **WHEN** `TOKEN` was changed in Bitwarden after the last pull and the user did not edit it in `~/.env`
- **THEN** the push does not write the old `TOKEN` value back and the regenerated `~/.env` has the new one

#### Scenario: Changed on both sides
- **WHEN** `TOKEN` was changed in Bitwarden after the last pull and also in `~/.env`, and the user presses Enter at the conflict question
- **THEN** the item keeps its value

#### Scenario: Same change on both sides
- **WHEN** `TOKEN` was changed in Bitwarden after the last pull and set to the same new value in `~/.env`
- **THEN** the push shows no conflict for `TOKEN`, writes nothing for it, and the regenerated `~/.env` has that value
