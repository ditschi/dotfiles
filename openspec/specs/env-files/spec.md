# env-files Specification

## Purpose
Defines which env files the shell loads and how they are generated and parsed.

## Requirements

### Requirement: Env files loaded in order
The shell SHALL load exactly `~/.env`, `~/.env.host` and `~/.env.local`, in this order, with later files winning. Other `~/.env.*` files SHALL NOT be loaded.

#### Scenario: Same variable in two files
- **WHEN** a variable is set in `~/.env` and in `~/.env.local`
- **THEN** the value from `~/.env.local` is used

#### Scenario: Other env file
- **WHEN** a file such as `~/.env.other` exists
- **THEN** the shell does not load it

### Requirement: Generated and local files
`~/.env` (group and profile items) and `~/.env.host` (host item) SHALL be generated by `machine env pull` from Bitwarden (`env/groups/<group>`, `env/hosts/<hostname>`), and previous contents SHALL be backed up. `~/.env.local` SHALL be local-only. It SHALL never be overwritten, and SHALL be changed only by appending lines the user chose to keep locally.

#### Scenario: Pulling env files
- **WHEN** a user runs `machine env pull` and no local-only key is chosen to be kept locally
- **THEN** `~/.env` and `~/.env.host` are rewritten from Bitwarden after a backup, and `~/.env.local` is untouched

#### Scenario: Keeping a key locally
- **WHEN** the user picks "keep locally" for a local-only key
- **THEN** its line is appended to `~/.env.local` and the existing content of `~/.env.local` is unchanged

### Requirement: Loader formats
The loader SHALL source files that contain `export` lines. It SHALL parse plain `KEY=value` files without executing the values, and expand `${NAME}` the way Docker Compose does.

#### Scenario: Plain file
- **WHEN** a file contains `KEY=value` lines without `export`
- **THEN** the variables are set and no value is executed

### Requirement: Loader fixes too-open env files
When an env file grants any permission to group or others, the loader SHALL change its mode to `600`, SHALL print one line on stderr naming the file and the old mode, and SHALL load the file. When the mode cannot be changed, the loader SHALL print a warning with the `chmod 600` hint and SHALL still load the file. A mode without group or other bits SHALL be left unchanged.

#### Scenario: Open permissions
- **WHEN** an env file has mode `644`
- **THEN** the file has mode `600` afterwards, a line naming the file and `644` is printed on stderr, and the file is loaded

#### Scenario: Group or other bits only
- **WHEN** an env file has mode `044` or `604`
- **THEN** the file has mode `600` afterwards and is loaded

#### Scenario: Stricter mode
- **WHEN** an env file has mode `400`
- **THEN** its mode is unchanged and nothing is printed

#### Scenario: Mode cannot be changed
- **WHEN** an env file has mode `644` and changing the mode fails, for example because another user owns it
- **THEN** a warning with the `chmod 600` hint is printed and the file is loaded

### Requirement: Local-only keys are carried over
A key that an existing `~/.env` or `~/.env.host` sets, but that neither generated file nor `~/.env.local` sets, is a local-only key, unless the last pull wrote it from a Bitwarden item and the file left it unchanged. The sync SHALL write the generated file anyway and SHALL carry each unresolved local-only key over, unchanged, into a marked local-only section at the end of that file.

#### Scenario: Key not in Bitwarden
- **WHEN** `~/.env` sets `OPENROUTER_API_KEY`, no Bitwarden item or `~/.env.local` sets it, and the user does not resolve it
- **THEN** `~/.env` holds the current Bitwarden values and, in the local-only section, the original `OPENROUTER_API_KEY` line

#### Scenario: Key already in the local-only section
- **WHEN** a key is in the local-only section and still has no source
- **THEN** the next sync keeps it there unchanged

### Requirement: Nothing is moved without the user
The sync SHALL NOT add to Bitwarden, write to `~/.env.local` or drop a local-only key unless the user chose that for the key.

#### Scenario: No terminal
- **WHEN** the sync meets a local-only key without a terminal or with `--yes`
- **THEN** the key stays in the local-only section, `~/.env.local` and Bitwarden are unchanged, and an attention item is recorded

### Requirement: Choices for a local-only key
On a terminal and without `--yes`, `machine env pull`, `machine update` and `machine setup` SHALL ask for each local-only key, by number: add to Bitwarden, keep locally, remove, or skip. The prompt SHALL name the key, the file and the Bitwarden item of that file.

#### Scenario: Prompt for a group key
- **WHEN** an interactive sync meets a local-only key in `~/.env` on a `private` host
- **THEN** the choices name `env/groups/private` as the Bitwarden target

#### Scenario: Prompt for a host key
- **WHEN** an interactive sync meets a local-only key in `~/.env.host`
- **THEN** the choices name `env/hosts/<hostname>` as the Bitwarden target

#### Scenario: Remove
- **WHEN** the user picks "remove"
- **THEN** the key is in neither the generated file nor `~/.env.local`, and the backup still holds it

#### Scenario: Skip
- **WHEN** the user picks "skip"
- **THEN** the key is carried over into the local-only section and an attention item is recorded

### Requirement: Skip is preselected
The preselected choice for a local-only key SHALL be "skip", so that confirming without a choice changes nothing. When a local-only key has a recorded Bitwarden origin, the prompt SHALL say which item set it before; this origin SHALL be kept when the key is carried over.

#### Scenario: Confirming the default
- **WHEN** the user presses Enter at the prompt for a local-only key
- **THEN** the key is carried over into the local-only section and nothing is moved

#### Scenario: Key deleted in the vault
- **WHEN** the local-only section holds a key with the origin `env/groups/private` and the item still does not set it
- **THEN** the prompt says the key was in `env/groups/private`, and after a skip the next prompt still says so

### Requirement: Adding a key to Bitwarden
"Add to Bitwarden" SHALL append the original line to the notes of the item that belongs to the file, under a comment that names the host and the date, then sync and regenerate the file. If the write fails, the key SHALL be handled as skipped and the failure reported.

#### Scenario: Successful write
- **WHEN** the user adds `OPENROUTER_API_KEY` from `~/.env` to Bitwarden
- **THEN** the notes of `env/groups/<group>` end with the origin comment and the original line, and the regenerated `~/.env` sets the key from that item outside the local-only section

#### Scenario: Write fails
- **WHEN** writing the item fails
- **THEN** the key stays in the local-only section, an attention item is recorded and the failure is reported

### Requirement: Shell code in an env file
When an existing `~/.env` or `~/.env.host` holds lines that are neither comments nor assignments, the sync SHALL leave that file unchanged and record an attention item. Its choices SHALL be keep locally, remove or skip; there is no Bitwarden choice.

#### Scenario: Conditional block
- **WHEN** `~/.env.host` contains an `if … fi` block
- **THEN** `~/.env.host` is unchanged, the other env file is still generated and an attention item names `~/.env.host`

### Requirement: Local-only keys never stop an update
Local-only keys or shell code in an env file SHALL NOT make `machine env pull`, `machine update` or `machine setup` abort, and SHALL NOT trigger a revert. The run SHALL print one short notice that names the keys, the file, the Bitwarden item, the backup and `machine attention` as the next command.

#### Scenario: Manual update with an unresolved key
- **WHEN** `machine update` runs, the env sync leaves a key unresolved and every other step succeeds
- **THEN** the later steps of the update run, the update succeeds and the notice names `machine attention`

### Requirement: Health check run leaves env file permissions alone
During the zsh health check run, the loader SHALL NOT change the mode of an env file and SHALL NOT print a permission message, so an open env file does not make the check fail.

#### Scenario: Open env file during the check
- **WHEN** the zsh health check runs and `~/.env` has mode `644`
- **THEN** the check passes, and `~/.env` still has mode `644` until the next real shell start

### Requirement: machine fixes too-open env files
`machine env pull`, and `machine setup` and `machine update` through it, SHALL change the mode of `~/.env`, `~/.env.host` and `~/.env.local` to `600` when group or other bits are set, and SHALL log each change with the file and the old mode. This SHALL also happen when Bitwarden is locked, `bw` is missing or the host has no context.

#### Scenario: Open file during an update
- **WHEN** `~/.env.local` has mode `664` and `machine update` runs with Bitwarden locked
- **THEN** `~/.env.local` has mode `600` afterwards and the output names it and `664`

#### Scenario: Nothing to fix
- **WHEN** all env files have mode `600`
- **THEN** `machine env pull` logs no permission change

### Requirement: Device group item
On a host with a context, `machine env pull` SHALL read the group item `env/groups/<context>` and then the device group item into `~/.env`: `env/groups/<context>-desktop` on the device `desktop`, `env/groups/<context>-server` on the device `server`. A key in the device item SHALL win over the same key in the group item. A missing device item SHALL be skipped like any missing item.

#### Scenario: Pull on a private desktop
- **WHEN** `env/groups/private` sets `EDITOR`, `env/groups/private-desktop` sets `GITHUB_TOKEN`, and `machine env pull` runs on a private desktop
- **THEN** `~/.env` sets `EDITOR` and `GITHUB_TOKEN`

#### Scenario: Pull on a private server
- **WHEN** the same items exist and `machine env pull` runs on a private server
- **THEN** `~/.env` sets `EDITOR`, does not set `GITHUB_TOKEN`, and `env/groups/private-desktop` is not read

#### Scenario: Pull on a work server
- **WHEN** `env/groups/work` sets `GITHUB_TOKEN`, `env/groups/work-server` sets `PROXY_URL`, and `machine env pull` runs on a work server
- **THEN** `~/.env` sets `GITHUB_TOKEN` and `PROXY_URL`, and `env/groups/work-desktop` is not read

#### Scenario: Server item
- **WHEN** `env/groups/private-server` sets `COMPOSE_PROFILES` and the host is a private server
- **THEN** `~/.env` sets `COMPOSE_PROFILES`, and a private desktop does not

#### Scenario: Device item missing
- **WHEN** `env/groups/private-server` does not exist and the host is a private server
- **THEN** the pull writes `~/.env` from `env/groups/private` and logs the missing item as skipped

### Requirement: A key deleted in Bitwarden follows Bitwarden
When the last pull wrote a key from a Bitwarden item, the file still holds that line unchanged, and no source read on the host sets the key now, the next pull SHALL remove the key without asking, on every host. It SHALL NOT be carried over as a local-only key. Logs SHALL name the key, never its value.

#### Scenario: Key moved in Bitwarden
- **WHEN** the owner moves `GITHUB_TOKEN` from `env/groups/private` to `env/groups/private-desktop` and `machine env pull` runs without a terminal
- **THEN** private desktops still set it, private servers no longer do, and `machine attention` names no local-only key for it

#### Scenario: Key deleted in Bitwarden on a desktop
- **WHEN** `EDITOR` is deleted from `env/groups/private` and `~/.env` on a desktop holds the line from the last pull unchanged
- **THEN** the next pull removes `EDITOR` from `~/.env`

### Requirement: A local edit of a deleted key is a conflict
When the file changed a key since the last pull and Bitwarden no longer sets it, the pull SHALL treat it as a local edit: in a terminal it SHALL offer push, discard or skip; without a terminal it SHALL leave the file unchanged and record an attention item.

#### Scenario: Edited locally, deleted in Bitwarden
- **WHEN** `EDITOR` was changed in `~/.env` after the last pull and deleted from `env/groups/private`, and the pull runs without a terminal
- **THEN** `~/.env` is unchanged and `machine attention` names the local edit of `EDITOR`

### Requirement: A local removal goes back with push
When the file removed a key since the last pull and Bitwarden still sets it, the pull SHALL treat it as a local edit, and `machine env push` SHALL offer to remove the key from the item that sets it.

#### Scenario: Removed locally
- **WHEN** the owner deletes the `EDITOR` line from `~/.env` and runs `machine env push`
- **THEN** push asks whether to remove `EDITOR` from `env/groups/private`

### Requirement: Backup leaves out keys deleted in Bitwarden
The backup that a pull makes of an env file SHALL NOT contain the lines it removes because Bitwarden no longer sets them.

#### Scenario: Backup after the token moved
- **WHEN** a pull on a private server removes `GITHUB_TOKEN` from `~/.env`
- **THEN** the new backup of `~/.env` does not set `GITHUB_TOKEN`

### Requirement: Push returns a key to its device item
`machine env push` SHALL write a changed key back to the item whose section in `~/.env` holds it, including a device group item.

#### Scenario: Change the token on a desktop
- **WHEN** the owner changes `GITHUB_TOKEN` in `~/.env` on a private desktop and runs `machine env push`
- **THEN** `env/groups/private-desktop` holds the new value and `env/groups/private` is unchanged
